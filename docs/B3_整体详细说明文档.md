# AutoGrader B3 整体详细说明文档

## 1. 项目是什么

`AutoGrader` 是一个“作业代码自动评分系统”课程项目，整体按模块拆分为：

- `B1`：学生信息、作业提交、成绩展示等前台管理能力
- `B2`：待测代码接收、测评流程、结果记录
- `B3`：题库管理、测试框架、评测规则与结果生成
- `B4`：数据库与基础后端支撑

本仓库实现的是 `B3` 模块的后端服务，核心职责不是“收作业”或“展示成绩”，而是：

- 管理题目和测试用例
- 定义每道题怎么判
- 对提交内容做安全检查
- 在受控环境里执行答案
- 生成总体与细节评测结果
- 把评测记录写入数据库

可以把 `B3` 理解成整个系统里的“判题规则中心”和“题库中心”。

---

## 2. 这个项目解决了什么问题

最开始的版本主要依赖静态规则判断答案，例如：

- 看用户是否用了某个命令
- 看命令顺序是否大致正确
- 看脚本文本里有没有某些关键字

这种方式实现快，但问题也很明显：

- 用户代码不一定真的能运行成功
- 很难验证文件是否真的被改对
- 很难验证脚本是否真的输出了预期结果
- 题目稍微复杂一点，纯静态规则就不够用了

所以现在这版 B3 做了一个关键升级：

**从“静态规则判题演示版”升级为“动态执行判题版”。**

也就是说，现在系统会把用户提交放到受控环境里真正执行，再根据：

- 标准输出
- 错误输出
- 退出码
- 运行耗时
- 生成或修改后的文件
- API 调用结果

来决定是否通过。

这就更接近一个简单的 `OJ` 判题系统。

## 3. 当前项目覆盖范围

本仓库当前主要覆盖 `problem.txt` 中的：

- `Q02` 到 `Q10`

另外还保留了一个演示题：

- `API_DEMO`

- Python 代码导入

这一类“接口调用型题目”的能力。

## 4. 整体架构

从职责上，这个项目可以拆成 6 层：

### 4.1 接口层

由 [main.py](/home/lenovo/b3/app/main.py) 提供 FastAPI 路由，负责：

- 接收 HTTP 请求
- 校验请求参数
- 调用 service 层
- 返回统一 JSON 响应

### 4.2 业务服务层

由 [question_service.py](/home/lenovo/b3/app/services/question_service.py) 和 [evaluation_service.py](/home/lenovo/b3/app/services/evaluation_service.py) 组成，负责：

- 题库导入
- 题目查询
- 判题入口调度
- 评测结果持久化

### 4.3 安全检查层

由 [security_checks.py](/home/lenovo/b3/app/judge/security_checks.py) 负责，核心目标是：

- 在执行前先拦截明显危险的提交
- 避免高风险 shell 语法和危险命令进入运行阶段

### 4.4 判题执行层

由 [dynamic_runner.py](/home/lenovo/b3/app/judge/dynamic_runner.py) 和 [api_runner.py](/home/lenovo/b3/app/judge/api_runner.py) 负责，核心目标是：

- 根据题目类型搭建测试环境
- 真正运行用户提交
- 收集输出和副作用
- 生成单个测试用例的判定结果

### 4.5 沙盒层

由 [sandbox.py](/home/lenovo/b3/app/judge/sandbox.py) 负责，核心目标是：

- 屏蔽“到底是在 Docker 里跑，还是在本地受限子进程里跑”的差异
- 给上层提供统一的 `run()` 接口

### 4.6 数据层

由 [models.py](/home/lenovo/b3/app/models.py)、[db.py](/home/lenovo/b3/app/db.py)、Alembic 迁移组成，负责：

- ORM 模型定义
- 数据库连接
- 表结构管理
- 评测记录落库

## 6. 系统中的核心对象

### 6.1 Question

代表一道题，保存：

- 题目编号
- 标题
- 描述
- 题目类型
- 时间限制
- 内存限制
- 允许命令
- 判题元数据

### 6.2 TestCase

代表一道题的一个测试用例，保存：

- 输入数据
- 预期输出
- 输入文件树
- 预期文件树
- 权重
- 是否隐藏

### 6.3 EvaluationRecord

代表“一次提交”的总体评测结果，保存：

- 提交编号
- 题目编号
- 原始提交内容
- 总分
- 通过数
- 总用例数
- 总体评价
- 静态问题

### 6.4 EvaluationCaseResult

代表“一次提交里某个测试用例”的评测结果，保存：

- 用例 ID
- 描述
- 是否通过
- 单用例分数
- 实际输出
- 预期输出
- 错误信息
- 耗时

## 7. 数据库设计逻辑

本项目数据库很克制，核心只有 4 张表：

- `questions`
- `test_cases`
- `evaluation_records`
- `evaluation_case_results`

这样设计的思路是：

- `questions` 负责定义“要判什么”
- `test_cases` 负责定义“怎么判”
- `evaluation_records` 负责记录“这次提交整体怎么样”
- `evaluation_case_results` 负责记录“每个测试点具体怎么样”

它不是一个完整教务系统数据库，而是 B3 模块最小闭环所需的数据结构。

## 8. 题库是怎么生成的

题库导入不是简单把 `problem.txt` 整段塞进数据库，而是两步合并：

### 第一步：解析题面文字

由 [problem_parser.py](/home/lenovo/b3/app/problem_parser.py) 读取 `problem.txt`，按“第 N 题”切分出正文。

这个阶段得到的是：

- 题号
- 人能读懂的题面描述

### 第二步：补结构化判题蓝图

由 [seed_data.py](/home/lenovo/b3/app/seed_data.py) 提供：

- 题目类型
- 允许命令
- 测试用例
- 输入文件
- 预期输出
- 预期文件
- 特殊判题元数据

### 第三步：合并入库

由 [question_service.py](/home/lenovo/b3/app/services/question_service.py) 把：

- `problem.txt` 中的人类可读描述
- `seed_data.py` 中的结构化测试配置

合并成最终可导入数据库的题目对象。

这样做的好处是：

- 题面来源真实依赖原始文档
- 判题逻辑又不受纯文本题面的限制
- 可以继续维护复杂测试夹具

## 9. 题目类型设计

当前系统里有 4 类题：

### 9.1 command

命令型题，重点验证：

- 命令是否正确
- 顺序是否正确
- 输出是否正确

例如：

- `Q02`
- `Q03`
- `Q04`

### 9.2 file

文件型题，重点验证：

- 命令是否执行成功
- 文件内容有没有改对
- 文件是否复制 / 移动成功
- 权限是否正确

例如：

- `Q05`
- `Q06`
- `Q07`
- `Q08`
- `Q09`

### 9.3 script

脚本型题，重点验证：

- 脚本是否能真实运行
- 输出是否与预期一致
- 是否存在硬编码答案

例如：

- `Q10`

### 9.4 api

接口调用型题，重点验证：

- 用户提交的 Python 代码能否被执行
- 指定入口函数是否存在
- 用不同参数调用后结果是否正确

例如：

- `API_DEMO`

## 10. 一次评测请求是怎么走完整链路的

下面用 `POST /api/v1/b3/evaluate` 举例。

### 第 1 步：客户端提交答案

前端或调用方提交一个请求体：

```json
{
  "question_id": "Q05",
  "submitted_code": "head -5 week5_11.txt\ntail -5 week5_12.txt\nls -ali\ncp week5_14.log week5_14_dest\nmv week5_15.log week5_15.txt",
  "submission_id": "manual",
  "language": "shell"
}
```

### 第 2 步：FastAPI 进入接口层

[main.py](/home/lenovo/b3/app/main.py) 中的 `/api/v1/b3/evaluate` 路由会：

- 读取请求体
- 查数据库确认题目存在
- 调用 `evaluate_submission()`

### 第 3 步：业务层选择判题分支

[evaluation_service.py](/home/lenovo/b3/app/services/evaluation_service.py) 会先看题目类型：

- 如果是 `api`，走 `_evaluate_api()`
- 否则走 `_evaluate_shell()`

### 第 4 步：静态安全检查

对 `command`、`file`、`script` 题，会先调用：

- `scan_shell_code()`
- 或 `scan_script_code()`

检查内容包括：

- 危险命令
- 危险 shell 语法
- 路径穿越
- 可疑死循环
- 硬编码答案

如果静态检查不通过：

- 不进入执行阶段
- 直接生成失败结果
- 同时仍会返回 `case_results`
- 并把静态问题写入数据库

### 第 5 步：准备测试环境

如果静态检查通过，系统会针对每个测试用例调用：

- `run_shell_case()`
- 或 `run_api_case()`

对于 shell / file / script 题，[dynamic_runner.py](/home/lenovo/b3/app/judge/dynamic_runner.py) 会：

- 创建临时工作目录
- 把 `input_files_json` 写入目录
- 在 `bin/` 里按题目需要生成 mock 命令
- 把用户提交写成可执行脚本

### 第 6 步：进入沙盒执行

执行不是直接在宿主机裸跑，而是通过 [sandbox.py](/home/lenovo/b3/app/judge/sandbox.py)。

如果配置为：

- `local`
  - 用本地受限子进程执行
- `docker`
  - 用 Docker 容器执行
- `auto`
  - Docker 镜像存在就优先 Docker，否则回退本地

### 第 7 步：拿回执行结果

沙盒返回统一结果：

- `stdout`
- `stderr`
- `exit_code`
- `execution_time_ms`
- `timed_out`

### 第 8 步：做题目级校验

不同题目的校验方式不同：

- `Q02`
  - 看 mock `ssh` 记录的实际参数是否匹配
- `Q04`
  - 比对目录切换后的 `pwd` 输出和 `cat` 结果
- `Q05`
  - 同时验证输出和目标文件状态
- `Q06`
  - 验证 `vi` 参数痕迹、文件内容、权限位
- `Q07-Q09`
  - 比对真实文本处理结果
- `Q10`
  - 比对脚本真实输出
- `API_DEMO`
  - 调用 Python 函数并对比返回值

### 第 9 步：汇总得分

系统按测试用例权重累计：

- `passed_count`
- `total_count`
- `overall_score`

当前 `Q02-Q10` 大多只有一个主测试用例，所以通常会看到：

- `0`
- `100`

但架构本身支持多个测试用例和权重，也就是说理论上可以扩展出部分分。

### 第 10 步：结果落库并返回

[evaluation_service.py](/home/lenovo/b3/app/services/evaluation_service.py) 会把结果写入：

- `evaluation_records`
- `evaluation_case_results`

然后返回给前端统一结构：

- `overall_score`
- `passed_count`
- `total_count`
- `overall_comment`
- `static_issues`
- `case_results`

## 11. 安全控制是怎么设计的

这个项目的安全控制分两层。

### 11.1 第一层：静态检查

由 [security_checks.py](/home/lenovo/b3/app/judge/security_checks.py) 负责。

主要拦截：

- 危险命令
  - `rm`
  - `sudo`
  - `shutdown`
  - `curl`
  - `wget`
- 危险 shell 语法
  - `&&`
  - `||`
  - 重定向
  - 反引号
  - `${...}`
  - 未加引号的 `;`
  - 真正的 `$(...)` 命令替换
- 路径穿越
  - `../`
- 可能的死循环
  - `while true`
- 脚本硬编码答案

这层的目标是：

- 先挡住明显危险和明显作弊的内容

### 11.2 第二层：沙盒执行

即使静态检查通过，也不会直接在宿主机裸跑。

Docker 模式下会使用：

- 无网络
- 只读根文件系统
- 受限 CPU
- 受限内存
- 受限进程数
- 临时可写目录
- 非 root 用户

这层的目标是：

- 限制用户代码即使被执行，也只能在很小的受控范围内活动

### 11.3 第三层：按题目控制文件读写权限

对于文件题，系统现在不仅检查“结果对不对”，还会根据题目内容决定：

- 哪些输入文件只能读
- 哪些文件允许写

这部分配置保存在题目的 `metadata_json` 中，当前主要使用两类字段：

- `readonly_paths`
- `writable_paths`

执行时，[dynamic_runner.py](/home/lenovo/b3/app/judge/dynamic_runner.py) 会先把工作目录中的输入文件按题目元数据设置成对应权限：

- 只读文件会被设置为 `0444`
- 可写文件会被设置为 `0644`

但仅靠权限还不够，因为像 `sed -i` 这类命令可能通过“写临时文件再替换”的方式绕过单纯的文件只读限制。

所以系统又加了一层“只读文件快照校验”：

- 执行前对 `readonly_paths` 做内容快照
- 执行后再次比对
- 如果只读文件被修改、删除，或出现不符合预期的变化，就会直接判失败

这样就形成了两层保护：

- 权限限制
- 执行前后快照比对

它的目标不是做操作系统级强制访问控制，而是让判题行为更符合题意：

- 纯读取题只能读，不能改输入文件
- 允许修改的题只开放指定文件

## 12. Docker 在项目里是怎么用的

本项目里的 Docker 不是用来部署整个系统，而是专门做“判题沙盒”。

意思是：

- FastAPI 服务跑在宿主机
- MySQL 跑在宿主机
- 只有用户提交的待测代码，会被放进 Docker 容器里执行

判题容器镜像由 [judge.Dockerfile](/home/lenovo/b3/docker/judge.Dockerfile) 构建，里面预装了题目需要的基础命令：

- `bash`
- `coreutils`
- `gawk`
- `grep`
- `openssh-client`
- `python3`
- `sed`
- `util-linux`
- `vim`

沙盒运行时的大体策略是：

- 每次评测单独启动一个临时容器
- 把测试工作目录挂载到 `/workspace`
- 在 `/workspace` 中执行提交
- 执行结束后自动删除容器

这就是当前项目“像 OJ 一样运行答案”的核心。

## 13. 为什么有些题要 mock 命令

不是所有题都适合直接调用宿主环境或容器里的真实系统命令。

例如：

- `Q02` 的 `ssh`
  - 课程要求是验证命令写法，不是真的去连远程主机
- `Q03` 的 `who -b`、`uname -r`、`date`、`cal`
  - 如果完全依赖真实环境，不同机器输出会不同
- `Q06` 的 `vi`
  - 交互式编辑器不适合直接让自动判题进入交互模式

所以项目对这些命令使用了 mock 包装：

- 对外看起来像执行了该命令
- 实际上返回的是稳定、可预测的测试结果

这样做的好处是：

- 测试稳定
- 不依赖真实机器状态
- 不需要人工参与交互

## 14. 当前已支持的题目逻辑

验证 SSH 登录命令是否正确，使用 mock `ssh` 记录实际入参。

验证文件查看、复制、改名，既检查输出，也检查文件结果。

### `Q06`

验证：

- `vi` 参数驱动的编辑效果
- `chmod` 修改后的权限位

这题会明确允许修改：

- `week6_1.txt`
- `week6_2.dat`

验证 `grep` 和 `sort` 的组合文本处理结果。

输入文件 `week7.txt` 按只读处理。

### `Q08`

验证 `sed` 文本筛选与编号输出。

输入文件 `week8.txt` 按只读处理。

验证 `awk` 统计与筛选。

输入文件 `employee.txt` 按只读处理。

## 16. 返回结果为什么这样设计

当前评测结果统一返回：

```json
{
  "question_id": "Q05",
  "submission_id": "manual",
  "overall_score": 100.0,
  "passed_count": 1,
  "total_count": 1,
  "overall_comment": "答案通过。",
  "static_issues": [],
  "case_results": []
}
```

这样设计的原因是要同时满足两个需求：

### 16.1 给前端或调用方直接展示

调用方最关心：

- 总分
- 通过数
- 总体评价

### 16.2 保留足够的调试和分析信息

细节里还需要：

- 哪个测试点没过
- 实际输出是什么
- 预期输出是什么
- 是静态安全拦截，还是运行时失败
- 执行耗时是多少

所以返回被拆成：

- 顶层汇总
- 明细 `case_results`

## 17. 为什么测试里要强制用 SQLite 和 local 沙盒

测试文件中会显式设置：

- `DATABASE_URL=sqlite+pysqlite:///:memory:`
- `SANDBOX_BACKEND=local`

这样做不是为了绕过真实部署，而是为了保证自动化测试具备：

- 不依赖本机 MySQL
- 不依赖 Docker 镜像状态
- 不依赖外部环境
- 可重复
- 可快速运行

也就是说：

- 测试关注的是“代码逻辑是否正确”
- 部署验证才关注“MySQL 和 Docker 是否装好”

## 20. 这个项目最值得讲的亮点

如果要对外介绍，最值得强调的亮点有 4 个。

### 20.1 从静态规则升级到动态执行

这是项目最本质的升级，体现了系统真实可用性。

### 20.2 引入了受控沙盒

通过 Docker 或本地受限执行，把“直接跑用户代码”的风险降低了很多。

### 20.3 题面和测试蓝图分离

`problem.txt` 提供题面，`seed_data.py` 提供结构化判题夹具，这样既保留原始题面来源，也保留灵活测试能力。

### 20.4 结果可追踪

不只是返回一个通过/失败，而是完整记录：

- 静态问题
- 用例明细
- 输出差异
- 耗时
- 历史记录

## 21. 如果你要给别人从头讲一遍，可以怎么讲

可以按下面这条线讲：

1. 这是 AutoGrader 里的 B3 模块，负责题库和判题逻辑。
2. 最开始系统主要靠静态规则判题，但那样不能保证答案真的能运行。
3. 所以我们把 B3 改成了动态执行判题：先静态检查，再在沙盒里真实运行答案。
4. 题面来自 `problem.txt`，但测试数据和判题规则来自结构化蓝图 `seed_data.py`。
5. 收到评测请求后，系统先查题目，再按题型走不同执行器。
6. shell/file/script 题会在临时工作目录中准备输入文件、mock 命令和提交脚本。
7. 执行层通过 `sandbox.py` 统一调用 Docker 或本地受限子进程。
8. 跑完后系统拿到 stdout、stderr、退出码、耗时和文件结果，再做题目级校验。
9. 最终生成总体评分和每个测试点的细节结果，并写入数据库。
10. 这样就形成了题库管理、动态判题、结果落库的完整闭环。
