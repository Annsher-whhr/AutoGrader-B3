# 杨洲-第5周-安全策略初稿

## 1. 本周工作目标

按照第 5 周计划，本周主要负责 `B3` 模块的安全策略初稿。  
本周的目标不是一次性把所有安全问题完全做完，而是先把评测系统最核心的安全边界建立起来，保证后续文件型题、脚本题和接口型题的执行不会直接裸跑。

本周安全策略的设计思路是：

- 先做静态检查，尽量把明显危险的提交拦在执行前
- 再做受控执行，把真正运行过程限制在隔离环境中
- 最后保留评测记录，便于后续排查和规则迭代

## 2. 本周完成内容

### 2.1 完成 shell / script 题的静态安全检查初稿

本周已经完成了 shell 与脚本题的第一版静态检查规则，能够在提交执行前识别以下问题：

- 危险命令
- 不允许的 shell 拼接语法
- 路径越界访问
- 超长命令脚本
- 题目白名单之外的命令
- 疑似无限循环
- 直接硬编码标准答案

文件位置：

- `app/judge/security_checks.py`

当前已经纳入拦截范围的典型危险命令包括：

```python
DANGEROUS_TOKENS = {
    "rm", "sudo", "shutdown", "reboot",
    "mkfs", "curl", "wget", "nc", "netcat",
    "powershell", "cmd.exe"
}
```

同时也明确禁止了若干高风险 shell 语法：

- `&&`
- `||`
- `>`
- `>>`
- `<`
- `` ` ``
- `${`
- `|&`
- 未加引号的 `;`
- 命令替换 `$()`

### 2.2 完成 API 题的 Python 静态检查初稿

针对接口调用型题目，本周补充了基于 `AST` 的 Python 静态检查。  
目前主要拦截：

- 危险模块导入
- 高风险函数调用

文件位置：

- `app/judge/api_runner.py`

当前禁止的内容包括：

- 导入 `os`、`sys`、`subprocess`、`socket`、`ctypes`、`pathlib`、`shutil`
- 调用 `eval`、`exec`、`compile`、`__import__`、`open`

这部分的目标是防止用户通过 Python 代码直接访问系统资源、文件系统或网络能力。

### 2.3 完成沙箱执行方案初稿

除了静态检查，本周还完成了受控执行环境的基础设计与实现。  
当前 `B3` 的执行器已经不是直接在服务进程里裸跑用户提交，而是统一走沙箱抽象层。

文件位置：

- `app/judge/sandbox.py`

目前支持两种后端：

- `LocalSandbox`
- `DockerSandbox`

其中：

- 本地模式下尽量使用 `prlimit` 施加资源限制
- Docker 模式下提供更强隔离

Docker 方案中当前已经限制的内容包括：

- 无网络：`--network none`
- 只读根文件系统：`--read-only`
- CPU 限制：`--cpus 1`
- 内存限制：`--memory`
- 进程数限制：`--pids-limit 64`
- 独立临时目录：`--tmpfs /tmp`
- 只挂载本次评测工作目录到 `/workspace`

这说明安全策略已经从“只做文本规则”提升为“静态检查 + 执行隔离”的组合方案。

### 2.4 把安全检查接入统一评测流程

本周还完成了安全策略与评测主流程的接入。  
现在评测入口会先根据题目类型调用不同的安全检查逻辑，再决定是否进入动态执行阶段。

文件位置：

- `app/services/evaluation_service.py`

当前流程如下：

1. 读取题目类型
2. shell / script 题先做 `scan_shell_code()` 或 `scan_script_code()`
3. API 题先做 `AST` 检查
4. 若静态检查失败，直接返回评测结果并记录问题
5. 若检查通过，再进入沙盒执行

## 4. 本周是如何完成的

### 4.1 先做白名单和黑名单结合的静态检查

本周采用了“黑名单拦危险、白名单限范围”的实现方式。

例如对于 shell 题：

- 先检查是否含有危险语法和危险命令
- 再检查命令是否在当前题目允许列表中

这样做的好处是：

- 题目边界更清晰
- 不同题型可以复用同一套检查框架
- 后续扩充规则时不需要重写整个执行器

### 4.2 再用沙箱隔离动态执行

单靠静态规则并不够，因为用户提交可能绕过简单字符串检查。  
因此本周把动态执行统一收敛到沙箱层，由沙箱负责：

- 切换工作目录
- 注入环境变量
- 限时
- 限内存
- 限制执行环境能力

这使得上层评测逻辑只关心“怎么判”，而不需要直接处理系统隔离细节。

### 4.3 用自动化测试验证安全规则有效性

本周已经补了对应的自动化测试，验证规则不是停留在设计上，而是确实生效。

文件位置：

- `tests/test_app_extra.py`

本周重点验证了以下场景：

- `test_q02_disallowed_command_rejected_by_static_scan`
- `test_q02_forbidden_shell_syntax_rejected`
- `test_q10_path_escape_rejected_by_static_scan`
- `test_q10_infinite_loop_pattern_rejected`
- `test_api_demo_forbidden_import_rejected`
- `test_api_demo_timeout_isolated_from_main_process`

这些测试说明当前安全初稿已经能拦住不允许命令、危险拼接、路径越界、无限循环、危险导入以及执行超时等问题。
