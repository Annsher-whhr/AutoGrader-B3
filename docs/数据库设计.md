# B3 数据库设计

## 1. 文档说明

本文件用于说明 `AutoGrader` 项目中 `B3` 模块在项目起步阶段的数据库设计方案。  
当前目标不是设计一个完整教务系统数据库，而是围绕 `B3` 的职责，建立能够支撑题库维护、测试数据管理和评测结果记录的数据库模型。

本文件同时说明：

- 数据表设计
- 表之间的关系
- 字段设计思路
- 中间件使用情况

---

## 2. B3 数据库设计目标

`B3` 模块的数据库需要解决以下问题：

1. 如何保存题目基础信息
2. 如何保存每道题对应的测试用例
3. 如何保存一次提交的总体评测结果
4. 如何保存一次提交中每个测试点的明细结果

因此，数据库设计目标概括为：

- 支撑题库管理
- 支撑测试框架配置
- 支撑评测历史记录
- 支撑结果展示与后续追踪

---

## 3. 数据库选型

在当前阶段，推荐使用关系型数据库。

### 3.1 推荐数据库

- `MySQL`

### 3.2 选择理由

- 关系清晰
- 结构稳定
- 便于使用 ORM 管理
- 适合题目、测试用例、评测记录这类结构化数据

### 3.3 测试环境选择

在开发和测试阶段，可临时使用：

- `SQLite`

原因：

- 启动简单
- 适合本地快速测试

但正式联调和演示环境建议统一使用：

- `MySQL`

---

## 4. 数据库总体结构

结合 `B3` 功能需求，当前阶段建议设计以下 4 张核心表：

1. `questions`
2. `test_cases`
3. `evaluation_records`
4. `evaluation_case_results`

这 4 张表可以分别理解为：

- `questions`
  - 题目主表
- `test_cases`
  - 题目测试用例表
- `evaluation_records`
  - 一次提交的总体结果表
- `evaluation_case_results`
  - 单个测试用例的结果表

---

## 5. 数据表详细设计

## 5.1 题目表 `questions`

### 5.1.1 作用

保存题目的基础定义信息。

### 5.1.2 主要字段设计

| 字段名 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | varchar | 题目编号，如 `Q02` |
| `title` | varchar | 题目标题 |
| `description` | text | 题目描述 |
| `question_type` | varchar | 题目类型，如 command/file/script/api |
| `difficulty` | varchar | 难度级别 |
| `language` | varchar | 默认语言类型 |
| `time_limit_ms` | int | 时间限制 |
| `memory_limit_mb` | int | 内存限制 |
| `allowed_commands` | json | 允许命令列表 |
| `metadata_json` | json | 扩展元数据 |
| `status` | varchar | 题目状态 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

### 5.1.3 设计说明

`questions` 表主要解决“这道题是什么”的问题。  
其中：

- `allowed_commands` 用于命令白名单控制
- `metadata_json` 用于保存题目的扩展配置

例如可以在 `metadata_json` 中放：

- 输入文件只读路径
- 可写路径
- 接口调用入口名
- 特殊判题规则

---

## 5.2 测试用例表 `test_cases`

### 5.2.1 作用

保存每道题的测试用例配置。

### 5.2.2 主要字段设计

| 字段名 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |
| `question_id` | varchar | 所属题目编号 |
| `case_no` | int | 用例序号 |
| `description` | varchar | 用例描述 |
| `input_data` | text | 标准输入数据 |
| `expected_output` | text | 预期输出 |
| `score_weight` | float | 分值权重 |
| `input_files_json` | json | 输入文件结构 |
| `expected_files_json` | json | 预期文件结果 |
| `call_args_json` | json | 接口调用参数 |
| `is_hidden` | bool | 是否隐藏用例 |

### 5.2.3 设计说明

`test_cases` 表主要解决“这道题怎么测”的问题。  
不同题型可以通过不同字段组合实现：

- 命令行题：
  - 重点用 `input_data`、`expected_output`
- 文件题：
  - 重点用 `input_files_json`、`expected_files_json`
- 调用型题：
  - 重点用 `call_args_json`

---

## 5.3 评测记录表 `evaluation_records`

### 5.3.1 作用

保存“一次提交”的总体评测结果。

### 5.3.2 主要字段设计

| 字段名 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |
| `submission_id` | varchar | 提交编号 |
| `question_id` | varchar | 题目编号 |
| `submitted_code` | text | 提交的原始代码或命令 |
| `language` | varchar | 提交语言 |
| `overall_score` | float | 总分 |
| `passed_count` | int | 通过用例数 |
| `total_count` | int | 总用例数 |
| `overall_comment` | text | 总体评价 |
| `static_issues` | json | 静态问题列表 |
| `status` | varchar | 评测状态 |
| `created_at` | datetime | 创建时间 |

### 5.3.3 设计说明

该表用于记录一次完整提交的总体结果，便于：

- 查询历史记录
- 展示成绩结果
- 追踪某次提交出现的问题

---

## 5.4 单用例结果表 `evaluation_case_results`

### 5.4.1 作用

保存某次提交中每个测试用例的详细结果。

### 5.4.2 主要字段设计

| 字段名 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |
| `evaluation_id` | int | 所属评测记录编号 |
| `case_id` | varchar | 用例标识 |
| `description` | varchar | 用例描述 |
| `passed` | bool | 是否通过 |
| `score` | float | 单用例得分 |
| `actual_output` | text | 实际输出 |
| `expected_output` | text | 预期输出 |
| `error` | text | 错误信息 |
| `execution_time_ms` | float | 执行耗时 |

### 5.4.3 设计说明

该表主要支撑：

- 细节评价
- 结果溯源
- 调试分析

如果只有总体记录，没有单用例结果，就无法完整实现任务书中要求的“总体评价 + 细节评价”。

## 6. 数据表关系设计

## 6.1 `questions` 与 `test_cases`

关系：

- 一对多

含义：

- 一道题可以有多个测试用例

---

## 6.2 `questions` 与 `evaluation_records`

关系：

- 一对多

含义：

- 一道题可以被提交很多次
- 每次提交对应一条总体评测记录

---

## 6.3 `evaluation_records` 与 `evaluation_case_results`

关系：

- 一对多

含义：

- 一次提交可以包含多个测试用例结果

---

```text
   ├── test_cases

            └── evaluation_case_results
```

## 7. 设计原因说明

## 7.1 为什么不把所有数据塞进一张表

如果把题目、测试数据、提交结果全部放进一张表，会带来：

- 冗余过大
- 查询混乱
- 更新困难
- 扩展困难

因此需要将：

- 题目定义
- 测试用例配置
- 提交结果
- 用例明细

拆开管理。

---

## 7.2 为什么需要 `metadata_json`

因为不同题目的判题规则差异比较大。

例如后续可能需要保存：

- 某些输入文件只读
- 某些路径允许写
- 特定接口入口函数名
- 特殊输出比对方式

如果每增加一种题型都改表结构，会让数据库设计变得很重。  
因此当前阶段保留一个 `metadata_json` 扩展字段，更适合起步阶段快速迭代。

---

## 7.3 为什么需要单独的 `evaluation_case_results`

因为需求明确要求：

- 总体评价
- 细节评价

如果只保留总体分数，就无法回答：

- 哪个测试点没通过
- 实际输出和预期输出差在哪里
- 是超时、语法错误还是结果错误

因此必须单独保存 case 级明细。

---

## 8. 中间件的使用情况

## 8.1 当前阶段的结论

在项目起步阶段，`B3` **不强依赖消息中间件**。

当前设计以：

- HTTP 同步接口
- 数据库存储

作为主要实现方式。

### 原因

- 当前重点是先把题库与判题核心链路打通
- 同步接口更适合项目初期联调
- 中间件会增加部署和维护复杂度

---

## 8.2 后续可扩展中间件

如果后续业务规模扩大，可考虑引入：

- `Redis`
- `RabbitMQ`

可用于：

- 评测任务排队
- 异步判题
- 结果通知
- 缓存热点题目数据

但在当前周作业对应的项目起步阶段：

**中间件不是必须项。**

---

## 9. 数据库与其他模块的关系

## 9.1 与 B2 的关系

`B2` 通过 `B3` 的评测接口提交待测代码，`B3` 则通过数据库保存：

- 题库配置
- 评测记录
- 明细结果

## 9.2 与 B4 的关系

`B4` 负责数据库环境与基础维护，`B3` 依赖 `B4` 提供：

- 数据库服务可用性
- 表结构迁移支持
- 统一后端支撑

## 9.3 与 B1 的关系

`B1` 更多是结果展示端，后续可以通过 `B2` 或直接通过接口读取评测结果。

---

## 10. 阶段性结论

在项目起步阶段，`B3` 的数据库设计以“够用、清晰、便于扩展”为原则，采用 4 张核心表即可支撑：

- 题库维护
- 测试用例维护
- 评测结果记录
- 细节结果记录

同时，在中间件使用上保持轻量化，优先以：

- HTTP 接口
- 关系型数据库

构建 `B3` 的最小可用闭环。
