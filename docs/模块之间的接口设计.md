# B3 模块之间的接口设计

## 1. 文档说明

本文件用于说明 `AutoGrader` 项目中 `B3` 与其他模块之间的接口设计方案。  
当前阶段按“项目起步阶段”进行设计，因此本文件重点描述接口边界、调用方向、数据格式和联调约定，而不强调具体代码实现。

`B3` 的外部协作对象主要包括：

- `B1`：前台与学生操作相关模块
- `B2`：代码接收与测评流程模块
- `B4`：数据库与后端基础支撑模块

---

## 2. B3 与其他模块的关系

## 2.1 与 B1 的关系

`B1` 主要面向学生或教师界面。  
`B1` 与 `B3` 的关系主要是“查询型”和“展示型”：

- 查询题目信息
- 查询测试说明
- 展示判题结果或明细结果

说明：

- `B1` 不直接负责判题逻辑
- `B1` 更像 `B3` 的调用方和结果展示方

---

## 2.2 与 B2 的关系

`B2` 负责接收待测代码，是与 `B3` 联动最紧密的模块。

`B2` 与 `B3` 的主要关系是：

- `B2` 接收学生提交的待测代码
- `B2` 将题号、语言、提交内容等转发给 `B3`
- `B3` 完成判题后把结果返回给 `B2`
- `B2` 再进行结果管理、展示或导出

说明：

- `B2` 是“测评流程入口”
- `B3` 是“判题规则与执行中心”

---

## 2.3 与 B4 的关系

`B4` 主要负责数据库与后端基础支撑。

`B4` 与 `B3` 的关系主要体现在：

- 数据库环境支持
- 表结构维护
- 统一接口规范
- 可能的用户管理和权限支撑

说明：

- `B3` 业务上独立
- 但底层需要依赖 `B4` 提供数据库环境和基础管理支撑

---

## 3. 接口设计原则

`B3` 接口设计遵循以下原则：

### 3.1 统一使用 HTTP API

模块间调用统一通过 REST 风格 HTTP 接口完成，便于：

- 本地联调
- 前后端分离
- 模块独立部署

### 3.2 请求与返回使用 JSON

统一使用 JSON，便于：

- B1/B2/B4 解析
- 接口文档统一
- 后续扩展字段

### 3.3 结果结构统一

评测相关接口统一返回：

- 总分
- 通过数
- 总用例数
- 总体评价
- 静态问题
- 测试用例明细

### 3.4 可扩展

在项目起步阶段，先保证：

- 核心字段稳定
- 路径清晰
- 便于后续补鉴权、补消息队列、补导出功能

---

## 4. B3 对外接口设计

以下接口是 `B3` 提供给其他模块调用的核心接口。

## 4.1 健康检查接口

### 接口说明

- 方法：`GET`
- 路径：`/health`

### 功能

用于判断 `B3` 服务是否启动成功。

### 返回示例

```json
{
  "status": "ok"
}
```

### 主要调用方

- `B2`
- 运维人员
- 联调人员

---

## 4.2 题库导入接口

### 接口说明

- 方法：`POST`
- 路径：`/api/v1/b3/questions/import/problem-txt`

### 功能

将原始题面和预置测试配置导入题库。

### 主要调用场景

- 新环境初始化
- 题库首次建立

### 主要调用方

- `B3` 维护者
- 运维人员

说明：

该接口不属于学生端业务流程，属于环境初始化接口。

---

## 4.3 查询题目列表接口

### 接口说明

- 方法：`GET`
- 路径：`/api/v1/b3/questions`

### 功能

返回当前题库中的全部题目列表。

### 返回内容建议包含

- 题目编号
- 标题
- 题目描述
- 题目类型
- 难度
- 状态

### 主要调用方

- `B1`
- `B2`

### 使用目的

- 展示题目列表
- 选择题目编号
- 做题库同步

---

## 4.4 查询题目详情接口

### 接口说明

- 方法：`GET`
- 路径：`/api/v1/b3/questions/{question_id}`

### 功能

查询某道题的详细信息。

### 返回内容建议包含

- 题目基础信息
- 时间限制
- 内存限制
- 允许命令
- 题目元数据
- 测试用例

### 主要调用方

- `B1`
- `B2`
- 教师维护端

---

## 4.5 查询测试用例接口

### 接口说明

- 方法：`GET`
- 路径：`/api/v1/b3/questions/{question_id}/cases`

### 功能

返回指定题目的测试用例列表。

### 主要调用方

- `B3` 维护人员
- 联调人员

说明：

该接口更适合测试与维护，不一定直接提供给学生端。

---

## 4.6 更新题目接口

### 接口说明

- 方法：`PUT`
- 路径：`/api/v1/b3/questions/{question_id}`

### 功能

更新题目的基础信息或元数据。

### 主要调用方

- 教师维护端
- 题库维护人员

### 更新内容建议包含

- 标题
- 描述
- 难度
- 时间限制
- 内存限制
- 状态
- 判题元数据

---

## 4.7 正式评测接口

### 接口说明

- 方法：`POST`
- 路径：`/api/v1/b3/evaluate`

### 功能

接收待测答案并完成正式评测。

### 请求体设计

建议请求体至少包括：

```json
{
  "question_id": "Q05",
  "submitted_code": "用户提交的代码或命令",
  "submission_id": "业务侧提交编号",
  "language": "shell"
}
```

### 字段说明

- `question_id`
  - 题目编号
- `submitted_code`
  - 待测答案内容
- `submission_id`
  - 本次提交的业务编号
- `language`
  - 语言类型或题目执行类型标识

### 返回体设计

建议返回：

```json
{
  "question_id": "Q05",
  "submission_id": "sub-001",
  "overall_score": 100.0,
  "passed_count": 1,
  "total_count": 1,
  "overall_comment": "答案通过。",
  "static_issues": [],
  "case_results": []
}
```

### 主要调用方

- `B2`

### 说明

这是 `B3` 最核心的业务接口。

---

## 4.8 参考答案自测接口

### 接口说明

- 方法：`POST`
- 路径：`/api/v1/b3/evaluate/answer/{question_id}`

### 功能

使用系统内置参考答案对某题进行自测。

### 主要用途

- 联调前验证判题逻辑
- 演示时快速验证
- 题库维护时做自检

### 主要调用方

- `B3` 开发组
- 联调人员

说明：

该接口更偏向开发和维护用途，不是正式业务接口。

---

## 5. B2 调用 B3 的接口流程设计

结合项目任务书，推荐 `B2 -> B3` 的调用流程如下：

### 步骤 1：B2 接收待测代码

来源可能包括：

- `B1` 转发的学生提交
- 电子邮件解析结果

### 步骤 2：B2 整理评测请求

请求数据包括：

- 题目编号
- 提交代码
- 业务侧提交编号
- 语言标识

### 步骤 3：B2 调用 B3 正式评测接口

调用：

```text
POST /api/v1/b3/evaluate
```

### 步骤 4：B3 返回评测结果

返回：

- 总分
- 通过数
- 总体评价
- 静态问题
- case 明细

### 步骤 5：B2 做后续处理

例如：

- 存储结果
- 展示结果
- 导出结果

---

## 6. B1 调用 B3 的接口流程设计

`B1` 与 `B3` 的直接交互通常不是“正式判题”，而是“读取信息”和“展示结果”。

推荐流程如下：

### 场景 1：题目展示

`B1` 调用：

- `GET /api/v1/b3/questions`
- `GET /api/v1/b3/questions/{question_id}`

### 场景 2：结果展示

`B1` 一般可以通过 `B2` 间接获得评测结果；  
如果后续系统设计允许，也可以直接调用 `B3` 的结果查询接口。

说明：

项目起步阶段优先保持：

- `B1` 负责页面
- `B2` 负责业务流程
- `B3` 负责题库与判题

这样职责更清晰。

---

## 7. B3 与 B4 的接口和协作设计

`B4` 更偏基础设施与后端管理，和 `B3` 的接口主要表现为“数据和运行环境支撑”，而不是大量业务接口互调。

当前阶段主要协作点包括：

### 7.1 数据库支持

`B4` 负责或协助提供：

- 数据库运行环境
- 表结构迁移支持
- 数据库用户与权限管理

### 7.2 统一接口规范

双方需统一：

- API 风格
- 状态码约定
- JSON 返回格式

### 7.3 后续扩展接口

如果后续需要实现：

- 用户权限管理
- 提交记录统一查询
- 结果导出

则 `B4` 可能为 `B3` 提供统一支撑接口。

---

## 8. 错误处理与接口约定

为保证模块联调顺畅，建议统一以下约定。

## 8.1 题目不存在

返回：

- HTTP `404`
- 错误信息：`Question not found`

## 8.2 参数非法

返回：

- HTTP `422`

## 8.3 业务失败

对于评测失败、静态检查不通过、超时等业务情况，建议：

- 保持 HTTP `200`
- 在返回体中通过：
  - `overall_score`
  - `overall_comment`
  - `static_issues`
  - `case_results`
  表达失败原因

这样做的原因是：

- 接口层调用成功
- 业务层结果失败

两者应区分开。

---

## 9. 中间件与消息机制说明

在项目起步阶段，`B3` 暂不强依赖消息中间件。

原因：

- 当前优先实现题库和判题核心能力
- 同步 HTTP 接口已经足够支撑联调

后续如系统规模扩大，可考虑引入：

- `Redis`
- `RabbitMQ`

用于：

- 异步评测任务调度
- 结果通知
- 任务队列管理

但在当前阶段，中间件设计属于可选扩展项，不作为 `B3` 的必须实现部分。

---

## 10. 阶段性结论

在项目起步阶段，`B3` 对外接口应优先保证：

1. 题库查询接口可用
2. 正式评测接口结构稳定
3. 自测接口可用于联调
4. 与 `B2` 的评测调用链路清晰
5. 与 `B4` 的数据库依赖关系明确

从模块协作角度看，最关键的一条接口链路是：

**B2 接收提交 -> 调用 B3 判题 -> B3 返回统一结果 -> B2 存储与展示**

这条链路应作为后续联调的重点。
