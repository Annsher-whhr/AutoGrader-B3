# B3 模块功能各模块的详细设计和功能点与需求项的覆盖（对应）关系

## 1. 文档说明

本文件用于说明 `AutoGrader` 项目中 `B3` 模块在项目起步阶段的功能设计方案。  
`B3` 的模块定位是“题库管理与判题规则支撑模块”，主要负责：

- 题目与测试数据的管理
- 不同题型测试框架的设计
- 提交答案的安全确认
- 评测结果的生成与返回

根据任务书，`B3` 对应的需求项主要包括：

- `RQ-B-3-10` 待测代码安全性确认
- `RQ-B-3-20` 实现以下类型题目测试框架
- `RQ-B-3-30` 待测代码由命令行接收测试数据
- `RQ-B-3-40` 待测代码由文件读取测试数据
- `RQ-B-3-50` 待测代码实现了某种调用接口，需要经过 import/include 等操作后才能调用并测试
- `RQ-B-3-60` 题库维护
- `RQ-B-3-70` 生成答案代码评价结果，包含总体评价与细节评价

本设计文档按上述需求将 `B3` 拆分为若干功能子模块，并建立需求覆盖关系。

---

## 2. B3 模块总体功能划分

结合需求内容，`B3` 拟划分为以下 5 个功能子模块：

1. 题库维护子模块
2. 代码安全确认子模块
3. 测试框架子模块
4. 评测执行与分析子模块
5. 结果生成子模块

这样的划分逻辑是：

- 先解决“题目和测试数据从哪里来”
- 再解决“待测代码能不能安全进入评测流程”
- 再解决“不同类型题目怎么测”
- 最后解决“评测结果怎么组织、怎么输出”

## 3. 各功能模块详细设计

## 3.1 题库维护子模块

### 3.1.1 功能定位

题库维护子模块负责题目信息、测试数据以及题目元数据的统一管理，是 `B3` 的基础数据来源。

### 3.1.2 主要功能

- 维护题目基础信息
- 维护题目分类与题型
- 维护每道题的测试用例
- 支持导入题面文本
- 支持题目列表查询、详情查询和更新

### 3.1.3 输入

- 原始题面文档
- 教师或维护人员录入的测试数据
- 判题所需元数据

### 3.1.4 输出

- 结构化题目信息
- 结构化测试用例
- 对其他模块可用的题目配置

### 3.1.5 设计要点

- 题目基础描述与测试夹具分离
- 支持后续扩展新题型
- 支持题目状态管理，例如启用、停用

### 3.1.6 拟采用的实现方式

项目起步阶段，题库维护子模块计划按“题面数据”和“判题数据”分层维护：

1. 题面层
   - 保存题目编号、标题、描述、题型、难度等基础信息
   - 用于界面展示和教师维护
2. 测试层
   - 保存测试输入、预期输出、输入文件、权重等信息
   - 用于后续自动判题
3. 元数据层
   - 保存白名单命令、接口入口名、特殊判题规则、文件读写权限配置等扩展信息

维护流程计划如下：

1. 教师或维护人员录入题目
2. 为题目补充测试用例
3. 为特殊题目补充扩展元数据
4. 将结构化结果写入数据库

这样设计的原因是：

- 后续题目会持续增加
- 不同题型对测试数据的要求不同
- 如果题面和测试规则完全耦合，会导致后续维护成本很高

### 3.1.7 对应需求

- `RQ-B-3-60`

## 3.2 代码安全确认子模块

### 3.2.1 功能定位

代码安全确认子模块负责在真正执行待测代码之前，先进行静态检查，尽量把危险内容拦截在执行前。

### 3.2.2 主要功能

- 检查是否使用危险命令
- 检查是否使用不允许的 shell 语法
- 检查是否存在路径越界风险
- 检查脚本中是否存在明显死循环风险
- 检查是否存在明显作弊式硬编码答案
- 对接口调用型代码做基础静态语法检查

### 3.2.3 输入

- 用户提交的命令、脚本或代码文本
- 当前题目的题型定义
- 当前题目的允许命令列表

### 3.2.4 输出

- 安全检查结果
- 静态问题列表
- 是否允许进入后续动态评测

### 3.2.5 设计要点

- 静态检查不直接替代动态判题，只作为前置门禁
- 优先拦截高风险命令与高风险语法
- 需要能根据不同题型切换不同检查策略

### 3.2.6 拟采用的实现方式

代码安全确认子模块计划采用“题型分流 + 规则检查”的实现方式。

对于命令题和脚本题，优先检查：

- 是否使用不允许的命令
- 是否使用危险命令
- 是否出现危险 shell 语法
- 是否存在路径越界访问

对于调用型题，优先检查：

- 是否存在危险导入
- 是否调用高风险函数
- 是否存在明显语法错误

处理流程计划如下：

1. 获取题目允许的命令和规则
2. 对提交内容做静态扫描
3. 生成静态问题列表
4. 若风险过高，则直接终止后续执行
5. 若通过，则进入动态判题流程

这样设计的原因是：

- 静态检查成本低
- 可以尽早拦截高风险输入
- 能减少后续执行环境的压力

### 3.2.7 对应需求

- `RQ-B-3-10`

## 3.3 测试框架子模块

### 3.3.1 功能定位

测试框架子模块负责根据题目类型，组织不同的测试环境和执行方式。

### 3.3.2 题型划分

结合需求，当前计划支持三类测试框架：

#### 1. 命令行输入型

特点：

- 答案由命令行接收测试数据
- 常见于 shell 命令题
- 输出通常由标准输出比对

适配需求：

- `RQ-B-3-30`

#### 2. 文件读取型

特点：

- 程序或命令从文件中读取测试数据
- 需要构造输入文件环境
- 需要检查文件读写行为和执行后的文件状态

适配需求：

- `RQ-B-3-40`

#### 3. 接口调用型

特点：

- 用户提交的是某段可调用代码
- 需要经过 import/include 等方式装载
- 再通过约定的入口函数或接口进行测试

适配需求：

- `RQ-B-3-50`

### 3.3.3 主要功能

- 根据题型分配测试框架
- 构造临时测试环境
- 准备输入数据或输入文件
- 准备执行入口
- 组织标准输出、返回值或文件结果比对规则

### 3.3.4 设计要点

- 各题型统一抽象成“测试用例 + 执行器 + 结果判定器”
- 为后续扩展更多题型预留统一接口

### 3.3.5 拟采用的实现方式

测试框架子模块计划为三类题型分别设计执行方案。

#### 命令行输入型

设计思路：

- 将学生答案整理成命令序列
- 在受控工作目录中执行
- 通过标准输出与预期输出比对判定结果

适用场景：

- 基础 shell 命令题
- 命令组合题

#### 文件读取型

设计思路：

- 在临时目录中预先写入输入文件
- 让待测代码在该目录中运行
- 运行后对输出结果和文件状态进行联合检查

额外考虑：

- 部分题目输入文件只能只读
- 部分题目允许写入指定文件
- 需要预留文件权限控制设计

#### 接口调用型

设计思路：

- 将用户提交代码以模块方式装载
- 找到约定入口函数
- 用多个测试用例调用
- 比对返回值与预期结果

统一调度设计：

- 测试框架层不直接写死每道题逻辑
- 每个题目都由“题目类型 + 测试用例 + 元数据”共同驱动
- 后续新增题目时，优先通过补配置完成，而不是频繁重写整体流程

### 3.3.6 对应需求

- `RQ-B-3-20`
- `RQ-B-3-30`
- `RQ-B-3-40`
- `RQ-B-3-50`

## 3.4 评测执行与分析子模块

### 3.4.1 功能定位

评测执行与分析子模块负责真正运行待测代码，并根据测试结果进行判定。

### 3.4.2 主要功能

- 在受控环境中运行待测代码
- 记录执行时间、退出状态、输出结果
- 比较执行结果与预期结果
- 检查执行后的文件状态
- 对异常情况进行分类，例如超时、运行错误、结果错误

### 3.4.3 输入

- 题目配置
- 测试用例配置
- 用户提交内容

### 3.4.4 输出

- 每个测试用例的通过情况
- 每个测试用例的错误信息
- 每个测试用例的细节评测结果

### 3.4.5 设计要点

- 评测执行环境需要隔离
- 需要支持运行时间与资源限制
- 文件读取型题目需要考虑只读文件保护
- 接口调用型题目需要考虑动态装载与调用

### 3.4.6 运行环境设计

项目计划在后续实现中引入 Docker 作为判题沙箱。

原因如下：

1. 判题需要真正执行用户提交的命令或脚本，直接在宿主机执行风险较高
2. Docker 可以为每次评测提供独立容器，便于限制：
   - CPU
   - 内存
   - 进程数
   - 网络访问
   - 可写目录范围
3. 容器执行结束后可以直接销毁，便于保持环境干净

对于文件型题，计划结合 Docker 做两层保护：

1. 容器内受控工作目录
2. 按题目配置输入文件只读 / 可写权限

### 3.4.7 为什么需要 Linux 环境

`B3` 的题目对象主要是：

- Linux 命令
- bash shell
- grep、sed、awk、chmod、vi 等工具

因此判题环境必须尽量保证 Linux 语义一致。

需要 Linux 环境的原因主要有：

1. 命令行为依赖 Linux 工具链
2. 文件权限控制依赖 Linux 权限模型
3. shell 脚本运行依赖 bash 环境
4. Docker 判题镜像本身更适合在 Linux 环境下运行

因此在整体设计上，建议：

- 开发和联调尽量基于 Ubuntu 或 WSL2 Ubuntu
- 最终集成环境也应统一到 Linux 语义一致的运行环境

### 3.4.8 拟采用的执行流程

评测执行与分析子模块的预期流程如下：

1. 根据题目类型选择执行器
2. 创建临时工作目录
3. 准备输入文件与测试数据
4. 配置文件读写权限
5. 启动沙箱执行待测代码
6. 采集 stdout、stderr、退出码、耗时
7. 比较输出、文件状态和返回值
8. 生成每个测试点的判定结果

这样设计的好处是：

- 评测流程清晰
- 不同题型都能纳入统一主流程
- 后续便于扩展和调试

### 3.4.9 对应需求

- `RQ-B-3-20`
- `RQ-B-3-30`
- `RQ-B-3-40`
- `RQ-B-3-50`

## 3.5 结果生成子模块

### 3.5.1 功能定位

结果生成子模块负责将多个测试点的执行结果整理成统一的评测结果输出。

### 3.5.2 主要功能

- 汇总用例通过情况
- 生成总体评价
- 生成细节评价
- 统计总分、通过数、总用例数
- 组织统一返回结构

### 3.5.3 输出结构

计划至少包括：

- 总分
- 通过用例数
- 总用例数
- 总体评价
- 静态问题列表
- 各测试用例详细结果

### 3.5.4 设计要点

- 总体评价与细节评价并存
- 结果结构应便于前端展示和数据库存储

### 3.5.5 拟采用的实现方式

结果生成子模块计划采用“两层结果结构”：

1. 总体结果
   - 总分
   - 通过数
   - 总用例数
   - 总体评价
2. 明细结果
   - 每个测试用例是否通过
   - 每个测试用例的错误信息
   - 每个测试用例的实际输出与预期输出
   - 每个测试用例执行耗时

结果输出后，计划同时满足两类使用需求：

- 前端或其他模块直接展示
- 数据库存档，便于后续追踪

### 3.5.6 对应需求

- `RQ-B-3-70`

## 4.2 需求项详细覆盖说明

### `RQ-B-3-10`

该需求由“代码安全确认子模块”承接。  
在系统设计中，所有提交进入执行前必须先经过静态安全检查，避免危险命令和明显异常脚本直接进入运行阶段。

### `RQ-B-3-20`

该需求由“测试框架子模块”承接。  
系统需要将不同类型题目抽象成统一的测试框架，以便后续维护和扩展。

### `RQ-B-3-30`

该需求属于命令行输入型题目，计划通过 shell/命令执行器实现。

### `RQ-B-3-40`

该需求属于文件型题目，计划通过：

- 临时工作目录
- 输入文件生成
- 文件只读/可写控制
- 文件结果比对

完成测试。

### `RQ-B-3-50`

该需求属于调用型题目，计划通过动态装载和统一调用入口完成测试。

### `RQ-B-3-60`

该需求由“题库维护子模块”承接，是 `B3` 的基础能力之一。

### `RQ-B-3-70`

该需求由“结果生成子模块”承接，确保系统不是只给出“通过/失败”，而是同时给出：

- 总体评价
- 细节评价

## 5. 阶段性结论

在项目起步阶段，`B3` 的设计重点应放在：

1. 明确题库结构
2. 明确三类测试框架
3. 明确静态安全检查与动态执行的分工
4. 明确统一结果结构
5. 为后续与 `B2`、`B4` 联调预留接口

从当前需求分析看，`B3` 的功能边界已经比较清晰，后续开发应优先完成：

- 题库数据结构落地
- 测试框架骨架搭建
- 统一评测结果模型
